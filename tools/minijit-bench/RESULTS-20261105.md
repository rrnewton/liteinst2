# S3 component micro-benchmarks — first numbers (2026-11-05)

[who-am-i: musejit, host withheld. Owner: musejit (muse, devbig030)]

Standalone measurements for the plan's S3 parallel track. These are
component costs on real code bytes, **not** whole-program or
comparative DBT claims (no DR ratio is meaningful at this
granularity; the M3/M4 denominator work lives in the bake-off).

Provenance: branch `musejit/speed-20261105` (off liteinst2 main
`98a3ea10`), host withheld, AMD EPYC 9D85, kernel
`7.1.3-0_fbk0_0_g295ad0959f34`, 2026-11-05T16:14Z. Command:
`CARGO_INCREMENTAL=0 cargo run --release --manifest-path tools/minijit-bench/Cargo.toml`.
Input: executable PT_LOAD segment of `/lib64/libc.so.6`
(1,530,732 bytes; linear sweep 367,809 instructions, 0 skipped,
86,464 patch sites of which 74,732 branch sites). Every cell:
exactly 10 timed samples after 1 warmup; run 1 tabulated, run 2
medians agree within the stated stability note. The 1.5 MiB copies
are cache-resident across reps; the 256 MiB cells are the
DRAM-scale measurement.

## Results (run 1; median, IQR in the CSV emitted by the bench)

| component | result |
|---|---:|
| copy, 1.5 MiB plain / AVX2 / AVX2-NT | 39.1 / 39.5 / 39.3 GB/s |
| copy, 256 MiB plain / AVX2 / AVX2-NT | **71.4** / 23.0 / 27.6 GB/s |
| decode only (streaming Decoder) | 191 MB/s, 45.9 Minsn/s (8.01 ms/rep) |
| copy + scan, per-insn Decoder (P1a style) | 77 MB/s (19.8 ms/rep incremental scan) |
| copy + scan, streaming Decoder | 177 MB/s (8.6 ms/rep incremental scan) |
| patch jump only | 0.70 ns/site sparse, 0.72 ns/site dense |
| copy + patch jump | 1.04× plain copy sparse (748 sites); 2.45× dense (74,732 sites) |
| emit count stub only (47 B template) | 1.03 ns/site sparse, 1.13 ns/site dense |

Run 2 medians: copies 38.6/38.5/40.5 and 68.1/23.9/27.9 GB/s;
decode 191 MB/s; streaming scan 174 MB/s; patch 0.69–0.72 and
stub 1.04–1.08 ns/site. No samples discarded in either run.

## What this says (component budget, per 1.5 MiB segment)

- **Copy is not the problem, and hand-rolled AVX2 loses.** Rust's
  `copy_from_slice` (memcpy) beats both hand loops at DRAM scale
  by ~2.9× — the fast path should call the platform memcpy, not
  intrinsics, unless a future profile on the actual cache-arena
  allocator disagrees. Streaming copy of guest code costs
  ~0.04 ms of an ~8.7 ms copy+scan pass: **~0.5%**.
- **Decode dominates translation.** Streaming decode is
  ~8.0 ms (45.9 Minsn/s); classifying/scan adds ~0.6 ms. The
  P1a-style per-instruction `Decoder` construction more than
  doubles scan cost (19.8–23.0 ms incremental) — reusing one
  streaming decoder is the single largest measured lever today,
  worth ~2.4× on scan before any copy work matters.
- **Modifications do pay their own way at emission time.** A
  jump patch is ~0.7 ns/site and a count stub ~1.1 ns/site:
  sparse modification (1 in 100 branch sites) is within noise of
  plain copy (1.02–1.04×), and even patching *every* branch site
  in libc adds ~0.05 ms — two orders below decode. The dense
  ratio (2.3–2.5× of copy) looks large only because copy itself
  is nearly free; against an 8 ms decode it is under 1%.
- Consequence for S3 integration order: (1) streaming decoder
  reuse in discovery/translation, (2) memcpy-class block copy
  with patch-site overwrites (already the design; now justified),
  (3) only then micro-tune stub shapes. Execution-side stub cost
  (~1.8 ns/branch from the P1a fixture report, pre-poll) remains
  the dense-instrumentation lever, separate from emission cost
  measured here.

Not measured yet (named, not implied): protection-transition
costs on this allocator shape, arena sync, dispatch/exit costs at
whole-program scale, and any DR/Pin comparative number.
